# Normative Phase 2 execution rules

This supplement resolves the independent review's implementation choices. It takes precedence over earlier shorthand in ARCHITECTURE.md and POLICIES.md. The dataclasses remain the machine record shapes; these rules define the cross-record and asynchronous obligations that constructors cannot verify. No scheduler, client, controller loop, or experiment is implemented here. Parameters below require explicit effective configuration; their numerical values remain proposals until calibration/pilot freeze.

## Configuration and observation contract

All durations are positive finite integers in nanoseconds unless stated otherwise. Counts are integers, excluding booleans. Rates are finite nonnegative operations/s or bytes/s. Each effective configuration must name:

| Group | Required fields and constraints |
| --- | --- |
| Identity | policy name/version, mapping seed/hash encoding/bucket count, old/final node IDs, dataset/version/checksum, complete finite per-bucket key/size/expiry registry |
| Bounds | all `ResourceLimits` fields; registry total/per-bucket bounds; maximum object/encoded request/response bytes; metric queue capacity; no payload beyond the configured maximum |
| Timing | control interval `dt`, demand subwindow width `h`, retained subwindows `m`, demand/signal/residency maximum ages, request timeout, task lifetime, cleanup deadline, metric emit timeout and flush deadline |
| Attempts | identical foreground cache-read/DB-read/cache-write retry policies across policies; migration donor/DB/write retry policies; finite per-stage attempt counts and backoffs; no implicit driver/client retries |
| DB | calibrated equal-cost attempt capacity `C_safe`, reserve in attempts/s, external workload counter source, foreground estimator margin, old-owner lower-rate margin, per-bucket rate multiplier `alpha >= 1`, cold reserve `u_b >= 0` in logical misses/s |
| Pressure | each component's upper/lower latency, inflight/queue, and memory/eviction thresholds; lower <= upper; minimum samples; maximum sample age |
| Common sampling | interval `dt`; one same-query-mix DB probe per interval; one PING and one INFO per cache per interval; finite encoded-byte ceilings and attempt timeout; probe-specific thresholds; one observer task per service, no overlapping rounds or retries |
| Rates | initial fixed rates and adaptive ceilings for donor ops/bytes, DB ops, destination writes/bytes; additive increments `a >= 0`, unsafe donor multiplier `0 <= gamma < 1`, safe windows `k >= 1`; finite token-bucket bursts for each dimension |
| Admission | per-tick admission cap; fixed schedule origin/interval/count; finite task lifetime; common key-order mode (`demand`, `fifo_hash`, `recency`); no policy-specific leapfrogging |
| Outcomes | expansion deadline, fixed measurement horizon >= deadline + stability/drain allowance, stability duration/subwindow/minimum affected requests per subwindow, initial-state TTL tolerance and old-cache stability criterion |

Invalid or missing fields refuse execution. A byte burst must accommodate the largest encoded single operation; otherwise reject the configuration rather than wait forever for an impossible token grant. Rate zero disables a stage until a later action or its task deadline. No calibrated `C_safe` means functional smoke checks only, with no capacity/safety claim.

Demand windows are aligned to run origin, half-open `[start,end)`, and span exactly `m` complete subwindows. Samples at `end` belong to the next window. `last_seen_ns` must be inside the reported window. Snapshots copy bounded maps into immutable views; later submissions cannot alter a closed snapshot. Record demand at actual router submission, including requests that subsequently fail; generator non-submissions remain in offered accounting and invalidate capacity interpretation. Registration exposes dataset identities/sizes/expiry only, never future access times/counts. Overflow keys are explicit, non-warm unknown demand; a workload/registry mismatch is `invalid_measurement` for exact-coverage comparisons.

The controller receives current affected `bucket_states`, routing epoch, per-bucket upper request rates/reserves/coverage, foreground DB attempt estimate and timestamp, pending-admission reserve, and timestamped pressure. All bucket maps describe one snapshot. `ControllerAction` echoes the observed epoch and as-of timestamp; decision time is explicit. Duplicate windows cannot increment safe counters or earn another grant. At decision, recompute all ages using decision time; a snapshot that became stale after collection pauses adaptive admissions/work. Missing, insufficient-sample, or invalid signals are UNKNOWN, never SAFE.

For each component, classify a closed sample UNSAFE if any upper threshold is crossed, SAFE if all lower thresholds are satisfied with sufficient samples, otherwise retain the previous state (initial UNKNOWN). Signals beyond maximum age are STALE regardless of their stored state. The DB classifier includes actual attempt rate and DB queue/latency; donor includes foreground donor impact and background transfers; destination includes latency, occupied memory and evictions. Threshold values and sample minima are configuration, not an invitation to choose another classifier.

Pressure observability must not depend on migration already progressing. Starting in pre-event observation, every policy, including immediate, runs the SAME fixed sampler each `dt`: one read of a deterministic registered key through the actual DB query mix (no fill), plus one PING and one INFO per cache. INFO supplies memory/eviction state; PING supplies labeled probe latency. Use sample_pressure interfaces, no retries, one bounded observer task per service, background connection pools and finite fixed probe byte/operation grants independent of migration grants. Reserve their connection opportunities before discretionary work; never use foreground permits. No overlapping/catch-up rounds. Failed sampling is UNKNOWN/UNSAFE as appropriate, recorded; a probe never asserts key residency. Probing does not establish sustainable capacity.

Keep probe and real-operation latency classes separate with distinct thresholds; never blend PING and write latency. A fresh successful probe bundle, fresh resource/queue data and all available real-operation classes below lower thresholds can establish SAFE during actual workload idleness. Per-probe sample minima must be attainable under the fixed grant, and pre-event observation spans at least `k` rounds; otherwise refuse configuration. Missing/failed bundles cannot establish SAFE. This avoids idle-destination/DB bootstrap deadlock without treating absent telemetry as safety. Raw sample types/counters/timings/classifier reasons are mandatory event detail.

Sampler operations have unique accounting IDs and WorkClass OBSERVATION_CACHE or OBSERVATION_DATABASE, including failure/timeout. Fixed probe DB demand `O_upper` is at least the configured maximum one attempted read per `dt` plus any still-issued bounded work; it is neither foreground application demand nor discretionary warming. Charge it separately in DB admission/reconciliation. Cache sampling operations/bytes count against shared physical pools/resources and are reported separately. Capacity calibration and all comparisons retain this same measured overhead.

Use no smoothing beyond the exact retained demand window and a rolling maximum of the last `k` fresh closed foreground-DB attempt-rate samples plus the configured additive margin. That estimate includes unrelated DB attempts and all foreground retries, excludes discretionary/observation DB attempts, and is UNKNOWN until sufficient data exists. Per-bucket request-rate upper estimate is `alpha * (represented + overflow count) / window_seconds`. Coverage uses the same window/destination, counts the complete registry for key coverage, and leaves overflow demand cold. Stale demand yields no positive warmed coverage and blocks adaptive admission. These are causal heuristics, not statistical confidence bounds or guarantees.

## Atomic ownership and bounded budget publication

`OwnershipMap.publish(advances, expected_epoch=e)` validates every affected bucket, expected state, sequential nonempty path, and unique bucket before mutation. Invalid epoch/path/bucket rejects the entire batch. An empty batch leaves epoch unchanged. A nonempty valid batch publishes one immutable snapshot at `e+1`. Each `BucketAdvance.path` can contain several sequential states, allowing immediate cutover and all-at-once eligibility/admission without exposing intermediate owners. Transition events share the publication epoch and include path order. A request captures the snapshot once before any cache work; no later retry/fill changes its owner.

`MigrationScheduler.apply_action` installs absolute ceilings and a grant valid on `[decided_at, decided_at+valid_for)`. It rejects duplicate/older decision times and overlapping replenishment. A newer action replaces unissued grant; it never adds another full grant to existing tokens. On expiry, no new background I/O issues. Existing issued operations finish under their attempt/task deadlines and remain charged. The scheduler uses the run's shared rate/burst configuration plus these per-interval operation/byte maxima. Tokens refill only with monotonic elapsed time, are clamped to burst, and start empty at expansion for every policy. Increases must not mint initial burst credit. Decreases clamp unused tokens; zero pauses issuance.

Obtain all required operation tokens, conservative encoded-byte reservations, bounded worker/payload buffer capacity, and the appropriate connection permit before issue. Acquisition is one bounded scheduler operation with a fixed resource order (worker, payload reservation, destination reservation, source tokens, connection); release provisional reservations if issuance never occurs. Never hold a DB/cache connection while waiting for tokens, sleeping for backoff, writing metrics, or waiting on another service. Once issued, operation/byte tokens are consumed, including retries, cancelled/timed-out work and misses. Byte reservations are charged at a registry/protocol upper bound; actual application-protocol request/response bytes are separately recorded. Unknown actual bytes are null, never zero. Do not refund an issued reservation; this is intentionally conservative. Actual bytes above the declared bound are an invalid measurement and configuration defect.

`TransferBudget` explicitly limits destination write operations AND bytes. No DB/donor work starts without a corresponding bounded destination write/payload reservation. Donor pressure and destination pressure therefore have enforceable, separate limits. Capacity reserved for a read that misses/expires can be released if no write issued. Unused per-action grant expires; it cannot be carried into another control interval. Fixed controls ignore soft pressure but obey these same hard memory/concurrency/byte bounds and finite deadlines. Optional residency probes are disabled in the primary specification; an extension must add a separate charged destination-read grant equally across policies.

## Retry-aware DB admission without repeated use of allowance

All DB quantities are **issued attempts/s**, matching capacity calibration, including retries. Let `A` be the common maximum foreground DB attempts per logical miss. Define:

```text
N_upper_b = A * (R_upper_b * (1 - coverage_lower_b) + u_b)
I_b = max(0, N_upper_b - old_owner_db_rate_lower_b)
allowance = max(0, C_safe - reserve - F_upper - P_pending - W_planned - O_upper)
```

`F_upper` already contains old-owner attempts and unrelated DB traffic. Charge only the positive new-minus-old increment, never append the old bucket rate again. The old-owner lower estimate is `max(0,min(last k fresh old-owner bucket attempt rates)-configured lower-rate margin)` over the same closed windows/query mix as foreground estimation; insufficient/stale evidence yields zero credit. Each such attempt must be uniquely attributed to its captured old bucket; do not subtract unrelated demand or coalesced followers. Log any conservative overlap when zero/low credit overestimates the true net change. These are temporal heuristic bounds, not guarantees. Sum of credited bucket lower rates cannot exceed `F_upper`. No negative increment earns extra allowance. `W_planned` is the full maximum discretionary issued rate including retry attempts. Convert interval grants to rates using `dt`; finite bursts are separately bounded and logged. The heuristic does not promise protection against arbitrary bursts.

New admissions accumulate in a pending reserve `P_pending`: add each admitted `I_b` immediately and subtract it from subsequent ticks' allowance until a fresh foreground observation window starts at or after that bucket's cutover. At that point remove that pending reserve because its attempts are represented in `F_upper`. Hold the reserve if evidence is stale/missing. This avoids repeatedly spending allowance while the observed foreground rate still predates recent admissions; the temporary conservative overlap during a straddling window is recorded. A cap of zero or an unsafe observation admits none, including zero-estimated-cost candidates.

Validate unique candidate IDs and finite rates before selection. Eligible candidates are in ascending bucket ID; skip a candidate that does not fit and consider the next; stop at the common per-tick cap. All-at-once controls intentionally do not use this incremental-admission filter and may cause measured overload.

## Exact policy update and pass rules

At expansion, all warming policies capture the same finite affected registry and begin COPYING. No new tasks or extra migration passes are created later in the primary comparison. Within a pass, select the next unissued key by descending `window_count / object_bytes`, then descending last-seen, then `(bucket,key)`; unobserved registered keys have zero count/last-seen. Re-evaluate ranking only for unissued tasks at a new closed window. `fifo_hash` uses a persisted seeded key-hash order, `recency` uses last-seen then `(bucket,key)`. All policies use the same chosen mode. Active tasks are never reprioritized into duplicate work.

Adaptive rates and safe counters start at zero at expansion; common pressure sampling continues while migration pauses. For each fresh, strictly newer window, increment safe counters only when SAFE, resetting otherwise. Once a counter reaches `k`, increase its previous rate by `a` per fresh safe window up to its ceiling. DB UNSAFE/STALE/UNKNOWN or stale foreground/demand data zeros DB warming. Donor UNSAFE multiplies previous ops/bytes by `gamma`; STALE/UNKNOWN zeros them. Destination UNSAFE/STALE/UNKNOWN zeros destination grants and new donor/DB warming work. SAFE destination ramps writes/bytes. Repeated windows neither ramp nor replenish.

For joint and adaptive warming controls, cap DB warming by `max(0,C_safe-reserve-F_upper-P_pending-O_upper)` after ramping, then floor(rate * dt) to integer interval grants. Retries consume grants rather than increasing rate. Joint/adaptive admission pauses if ANY DB/donor/destination signal, foreground estimate or demand is stale/unknown/unsafe, or consecutive safe windows are insufficient. Warmup-only and adaptive-budget migration-before-cutover use the identical budget update but retain fixed/all-at-once admission. Traffic-only uses the same admission estimator/ages/safe-window rule with fixed warming. Fixed controls share hard maxima/bursts and foreground semantics, without adaptive soft-pressure gates.

A key pass has at most one donor-read stage, one optional DB fallback stage, and one destination-write stage, each with its finite retry count. Retry only transient connection/I/O errors and attempt timeouts, with exact configured backoffs and no jitter. Donor miss/expiry is not retried: move to DB fallback if enabled. Authoritative missing dataset key or wrong value is a correctness fault and invalidates the run. Exhaustion of a source stage moves to the next permitted source; exhaustion of write attempts ends `not_warmed`. DB fallback disabled, unavailable tokens until task lifetime expires, oversize payload, or expired value terminates `not_warmed` with its specific reason. Never re-read the source solely to restart an exhausted write stage. Task absolute deadline is `min(expansion+task_lifetime, handover_deadline)`; queue/token waits/backoff count against it.

Donor hits and DB reads use the registry's original expiry cap. A donor read reports an absolute expiry computed conservatively from a monotonic time taken before its atomic value+remaining-TTL read; local elapsed time is subtracted before write. The client must atomically read payload+TTL, preserve no-expiry distinctly, round destination TTL down, and never refresh the registry deadline on a DB refill. Expired values are not written or returned. Phase 3 must verify the actual adapter semantics against Redis. Database clients return registry expiry, not a newly minted TTL.

For migration-before-cutover, both fixed and adaptive, finish the entire finite pass, mark all affected buckets ELIGIBLE, then publish all NEW in one epoch. Missing/exhausted/expired keys are explicitly allowed cold and logged; do not claim full warm coverage. These are strong bounded donor+DB controls, not exact ElMem reproductions. For gradual controls, each bucket becomes ELIGIBLE when its own pass terminates; the fixed tick admits the next contiguous eligible prefix up to the tick cap. A blocked tick loses its opportunity; there is no catch-up credit and later buckets never leapfrog. Joint/traffic-only admission uses the estimator above after per-bucket eligibility. Immediate cutover uses a single multi-step publication, zero background grants, and no pass.

## Foreground coalescing, ownership and cleanup

All foreground time starts at scheduled arrival. If already past deadline at submission, capture a route for accounting and return TIMED_OUT without I/O. At the inflight bound, a received request is REFUSED (zero work, captured route); it is not hidden in an unbounded admission queue. Within the bound, cache/DB permit waits and coalescing-table waits use the remaining absolute deadline. Every hit must be checked for expiry. Retry only transient errors/timeouts; a cache miss proceeds to DB, not cache-read retries. Exhausted cache-read errors fail the request; no silent source fallback. An exhausted DB read fails the shared fill. Cache fill failure is recorded but does not discard a valid DB value if it can be returned before the request deadline.

The first miss creates a separate bounded fill task keyed by `(captured_owner,key)` and immutable originating request ID. Its deadline is the creator's original foreground deadline and is never extended by followers; it owns DB attempts and cache-fill attempts. Every waiter, including the creator, is shielded from cancelling that task while another waiter remains. A creator that times out/cancels detaches like any follower. A later-deadline follower may receive shared-fill failure at the creator's deadline; it does not silently launch a fresh retry tree. This is common to every policy. Once failed/completed, a later separate request may create a new entry.

When the final waiter leaves, cancel the fill even if I/O has issued. Issued work remains charged; cancellation does not prove the server stopped. Keep its worker/pool permit reserved until the driver confirms completion or the connection is closed/discarded. Bounded cancellation cleanup uses the common cleanup deadline. A connection with uncertain protocol state never returns to a pool; close/discard it before replacement. If confirmed cleanup cannot be achieved by the deadline, stop issuance and classify infrastructure/measurement failure rather than recycle a possibly active permit. No unbounded orphan task remains detached. Remove entries in `finally` only if the table still points to that generation's task, preventing old cleanup from deleting a newer fill.

Request records are emitted once at final reconciliation, after bounded draining. The originating request retains ownership of shared DB/write attempts even if it terminated before those attempts completed; its request terminal time stays unchanged. Followers have zero DB/write attempts and link the origin ID; cache-read attempts remain their own. Every issued operation also has a uniquely identified accounting event, so attempts completed after a request timeout are not lost. Retain completion/timeout/cancel outcomes and no-I/O refusals/non-submissions; there is no successful late response after the absolute deadline.

## Records, draining, reset, and success

`EventRecord.detail` carries structured versioned detail. For operation accounting it MUST contain unique `operation_id`, request/task ID, operation (`read`, `write`), source, target owner, work class, absolute deadline, issue/terminal times, outcome, reserved bytes, nullable actual bytes, and retry ordinal. For actions it contains the entire action, observation reference, rates, pending reserve and admission/rejection estimates. For transitions it contains expected epoch/states/path. A migration attempt record is the detailed view of the SAME operation ID referenced by its accounting event, not another operation to sum. Destination writes are explicit `NEW_CACHE / DESTINATION_WRITE` tasks with parent read-task linkage. Nonissued task terminal events carry disposition and reason, never an issued-operation charge.

All offers have deterministic IDs from a persisted offered schedule (manifest checksum/count) and an arrival event when due. Terminal records alone cannot prove no offers were omitted. Validate set equality against the independent schedule and uniqueness, every linked leader exists with matching captured owner/key, and global operation IDs reconcile to request leaders, unrelated foreground, and migration classes exactly once. In `RequestRecord`, `cache_attempts` means cache reads; `cache_write_attempts` means foreground fills. `source` is the returned source on success or the last attempted source on failure; NONE is allowed when no source was issued. `work_class` summarizes the most costly issued category (foreground DB if any, otherwise foreground cache), with per-operation events retaining the full breakdown. Followers that receive DB values use FOREGROUND_CACHE if their only issued work was a cache lookup.

The metrics queue is bounded. Emit outside connection/worker critical sections; bounded sink waits count in latency when response emission is delayed. Record overflow/failed durable flush as invalid measurement. At the fixed measurement horizon, stop generating new offers, preserve all scheduled offers, drain submitted work only to each request deadline and the common cleanup bound, then reconcile. At the handover deadline stop new background work and admissions; outstanding offered foreground requests still receive terminal records. Measurement horizon is identical across policies and does not end early on handover success.

Namespaces alone do NOT isolate Redis maxmemory/LRU/allocator history. Each comparative run must recreate the verified disposable research cache instances, then use a fresh namespace. Namespace-only resets on shared physical caches are allowed for functional diagnostics, never for fair policy comparisons. Verify service identity before any destructive reset; no broad flush against shared/unverified services. Pair dataset, ownership, deterministic warm-prefix order, workload/background seeds and relative TTL ages. Require a full sorted key/value/remaining-TTL summary of the small initial cache state, empty destination, equal configured memory/eviction limits, and identical warm-prefix execution. Recreate on mismatch; do not selectively delete keys or rewarm only one policy. Record allocator/memory/eviction counters and the pre-event stabilization rule; exact process scheduling/LRU equivalence remains a later measured limitation, not guaranteed by checksums. Sampled summaries cannot certify exact initial equivalence in the primary comparison.

After all affected buckets are NEW, begin a candidate stability interval composed of configured complete subwindows. Every subwindow requires at least the common minimum number of actual submitted affected requests; all capture the destination (including failures) and capture epochs at or after final publication. Record offered/submitted/completed affected counts, observed destination share, and expected share derived from the actual submitted key population. No success-percentile filter or future popularity oracle is used. An insufficient subwindow resets the candidate interval and logs `traffic_stability_inconclusive`; wrong post-cutover routing is a correctness fault. Success requires every subwindow for the entire stability duration before or exactly at the deadline; otherwise HANDOVER_TIMEOUT is a valid policy failure. Empty affected sets or workloads with no affected traffic are invalid configurations for expansion evaluation. All policies share this rule; success does not imply latency targets were met.

Phase 3 must implement and behaviorally test these contracts, including generation races, driver cancellation/pool discard, token reservations, real TTL behavior and fresh-instance resets. Phase 4 calibrates rate/pressure inputs; Phases 5/6 implement policies; Phase 7 freezes parameters and measurement rules. Contract tests cannot certify those future behaviors.
