# Phase 4 methodology: capacity calibration and immediate cutover

The testbed has two old Redis instances and one empty destination, all with 32 MiB `allkeys-lru` limits, plus a PostgreSQL 17 container limited to one CPU and 512 MiB. The 512 immutable 1 KiB objects occupy roughly 1.6 MiB per old Redis process after complete placement; no confirmation run reported Redis evictions. The destination begins physically empty. A complete deterministic old-cache preload and 128-read prefix must have zero misses before the measurement origin.

The actual DB query is an indexed key lookup with a deterministic `generate_series`/`md5` CPU expression evaluated in PostgreSQL. `query_cpu_rounds=20000` was selected from exploratory measurements and is recorded in every run configuration. It is an intentionally constrained query mix, not a model of a production query distribution. The relation is 606,208 bytes; the probe recorded 734 heap-buffer hits and zero heap-buffer reads after 96 same-mix reads, so this characterization is memory-resident. It is not an IO-bound database result.

Arrival schedules are absolute monotonic times. Offered means a persisted scheduled arrival; submitted means `router.read` began; issued means a DB connection was acquired and the real DB query began; completed means a terminal result was persisted. Load generation never waits for an earlier response before scheduling later offers. Analysis reports successful-request percentile latency from scheduled arrival and separately treats any non-completion or successful latency over the provisional 100 ms threshold as an all-offer violation.

For the immediate condition, all buckets whose final owner is `new` make one atomic `OLD -> COPYING -> ELIGIBLE -> NEW` transition at 3 seconds. There is no donor copy, database warm-up, diagnostic delete, forced miss, or old-cache fallback. The control uses the same seed, schedule, router, telemetry, pools, quotas, observation sampler, old-cache preparation and service recreation but does not publish the new routing epoch. Fixed windows are pre-event [0,3), transition [3,5), and post-event [5,8.5) seconds.

`C_safe=24` actual reads/s is selected only for this mix and resource setup: all three confirmation runs submitted and issued every offer, had p95 48.1--52.3 ms, and had zero all-offer violations. At 36 reads/s, two of three runs had p95 353--512 ms and together 260 violations; one third run was below the target, which is retained as observed variation. The rate is an empirical admission boundary, not a general database capacity or safety guarantee.

The router/cache/load-generator check is the matched 36-rps old-cache control: all 864 offered requests across three runs were submitted and completed, used no foreground DB reads, and transition-window p95 ranged 27.2--30.4 ms. Thus, at the expansion workload, the observed degradation is not explained by the client schedule falling behind, client pool exhaustion, Redis evictions, or router cache-hit work. This is capacity attribution at the tested rate, not a maximum router/Redis benchmark.
